# OpenChibiRig 项目规划文档（v0.1）

> 暂定名称：**OpenChibiRig**
> 项目定位：面向正面 Q 版角色立绘的开源自动拆层与基础绑定工具
> 文档版本：v0.1
> 更新日期：2026-07-30
> 当前阶段：需求定义与技术验证

## 1. 项目概述

OpenChibiRig 计划构建一个开源工具，将符合规范的正面 Q 版角色立绘，转换为具备基础动作的实时 2D 可动角色。

项目希望降低 2D 角色建模的入门门槛。用户不需要从零学习复杂的网格、变形器、参数和物理系统，也可以快速得到一个能够眨眼、说话、呼吸和轻微摆动的基础模型。

项目不以完全替代专业建模师为目标，而是自动完成重复性较强的基础工作，再由用户进行必要的检查和微调。

## 2. 项目目标

### 2.1 长期目标

输入一张符合规范的正面 Q 版全身立绘，自动完成：

1. 背景移除与角色区域检测；
2. 头发、脸部、五官、身体、衣服和四肢等部件拆分；
3. 被遮挡区域的基础补全；
4. 图层顺序推断；
5. 网格和变形器生成；
6. 基础动作参数绑定；
7. 头发和衣摆的简单物理效果；
8. 实时预览、人工修正和模型导出。

最终目标不是“任意图片一键生成商业级模型”，而是：

> 对符合输入规范的 Q 版正面角色，自动完成大部分基础拆层与绑定工作，生成一个可用且可继续编辑的 2D 人偶模型。

### 2.2 第一阶段目标

第一阶段暂不直接解决最困难的单图拆层问题。

首个可用版本优先支持：

```
规范化分层 PSD / PNG 图层目录
        ↓
自动识别图层角色
        ↓
自动生成网格和绑定参数
        ↓
生成基础动作与物理
        ↓
实时预览
        ↓
保存并重新加载模型
```

完成这一阶段后，再接入单张 PNG 自动拆层能力。

## 3. 目标用户

- 没有 2D 角色建模经验的个人用户；
- 独立 VTuber 和虚拟主播；
- 桌宠、虚拟助手和互动角色开发者；
- 独立游戏开发者；
- 希望快速预览立绘动态效果的画师；
- 需要批量生成基础角色模型的小型团队；
- 学习计算机视觉、图形学和角色动画的开发者。

## 4. 首版支持范围

### 4.1 输入角色要求

首版仅支持满足以下条件的角色：

- Q 版或接近 Q 版的二次元角色；
- 正面或接近正面视角；
- 全身或大部分身体完整可见；
- 中性站姿；
- 透明背景或纯色背景；
- 五官边界清晰；
- 左右眼和嘴巴可识别；
- 双手不能严重遮挡面部；
- 四肢不能大面积交叉；
- 头发、衣服和身体之间应有相对清晰的边界；
- 不包含复杂透视、强烈俯视或仰视。

“通用工具”表示不同角色只要符合以上规范就可以处理，不表示支持任意图片和任意画风。

### 4.2 首版基础动作

MVP 计划支持：

- 自动眨眼；
- 左右眼同步或独立开合；
- 眼球左右、上下移动；
- 嘴巴开合；
- 基于麦克风音量的简单口型；
- 呼吸起伏；
- 头部小幅左右倾斜；
- 身体轻微左右摆动；
- 前发、侧发、后发的简单摆动；
- 衣摆或丝带的简单物理效果；
- 默认待机动画。

### 4.3 首版暂不支持

- 大角度头部转动；
- 完整的 3D 透视模拟；
- 任意动作姿态；
- 自动生成复杂手势；
- 专业级 A/I/U/E/O 精细口型；
- 多套服装自动切换；
- 高精度情绪表情；
- 完全自动消除穿模和破图；
- 保证达到商业级专业模型质量；
- 将 Live2D Cubism 作为项目核心运行时。

## 5. 输入规范

### 5.1 v0.1 输入格式

首版支持以下两种输入：

1. 分层 PSD；
2. 包含透明 PNG 图层的文件夹或 ZIP。

推荐的基础图层结构：

```
character/
├── 010_back_hair.png
├── 020_body.png
├── 030_clothes.png
├── 040_face.png
├── 050_left_eye_white.png
├── 060_left_iris.png
├── 070_left_upper_eyelid.png
├── 080_right_eye_white.png
├── 090_right_iris.png
├── 100_right_upper_eyelid.png
├── 110_left_eyebrow.png
├── 120_right_eyebrow.png
├── 130_mouth.png
├── 140_front_hair.png
├── 150_left_side_hair.png
├── 160_right_side_hair.png
└── manifest.json
```

所有 PNG 图层应满足：

- RGBA 格式；
- 透明背景；
- 使用同一画布尺寸；
- 保留被其他部件遮挡的必要重叠区域；
- 图层命名遵守项目规范；
- 左右方向以角色自身方向为准，而不是观看者方向。

### 5.2 v0.2 输入格式

在自动绑定稳定后，增加：

- 单张透明 PNG；
- 单张纯色背景 PNG/JPEG；
- 自动输出分层 PSD 和项目中间文件。

## 6. 输出内容

首版输出应包括：

```
output/
├── project.json
├── layers/
├── masks/
├── meshes/
├── motions/
├── physics/
├── preview/
└── export/
```

计划提供以下输出能力：

1. 项目自定义开放格式；
2. 可重新加载和继续编辑的工程文件；
3. 分层 PNG 和图层清单；
4. 网格、参数、变形器和物理配置；
5. Web 或桌面实时预览；
6. 优先导出 Inochi2D / nijilive 等开放格式；
7. 后续以独立插件方式研究 Cubism 兼容导出。

## 7. 内部数据模型

项目需要先定义一个与具体运行时无关的中间格式，避免核心算法绑定在某个商业格式上。

示例：

```
{
  "format_version": "0.1",
  "canvas": {
    "width": 2048,
    "height": 2048
  },
  "layers": [
    {
      "id": "front_hair",
      "path": "layers/front_hair.png",
      "role": "hair.front",
      "draw_order": 140,
      "anchor": [1024, 760]
    }
  ],
  "landmarks": {
    "left_eye": [],
    "right_eye": [],
    "mouth": [],
    "face_contour": []
  },
  "meshes": [],
  "deformers": [],
  "parameters": [],
  "physics": [],
  "motions": []
}
```

该格式负责表达：

- 图层；
- 图层语义；
- 绘制顺序；
- 关键点；
- 网格顶点和三角形；
- 父子节点关系；
- 变形器；
- 参数；
- 参数关键帧；
- 物理链；
- 默认动作；
- 导出映射。

## 10. 开发路线

### Milestone 0：技术验证

目标：

- 选定 1 个亚托莉 Q 版角色作为固定测试样本；
- 手工准备规范分层；
- 读取全部图层并按正确顺序渲染；
- 使用简单网格让单个图层发生形变；
- 验证保存、加载和实时预览链路。

完成标准：

- 能正确还原角色；
- 能在预览器中控制一个测试参数；
- 工程文件可以保存后重新加载。

### Milestone 1：v0.1 自动绑定原型

输入：规范化分层 PSD 或 PNG 图层目录。

功能：

- 输入校验；
- 图层角色识别；
- 基础关键点配置；
- 网格自动生成；
- 自动眨眼；
- 嘴巴开合；
- 眼球移动；
- 呼吸；
- 头部倾斜；
- 身体待机摆动；
- 头发简单物理；
- 项目保存与重新加载。

### Milestone 2：v0.2 单图拆层

输入：正面 Q 版单张立绘。

功能：

- 背景移除；
- 语义拆层；
- 遮挡区域补全；
- 图层顺序推断；
- 拆层结果预览；
- 蒙版涂抹修正；
- 将结果交给 v0.1 自动绑定流程。

### Milestone 3：v0.3 可用编辑器

功能：

- 调整眼睛、嘴巴和脸部关键点；
- 修改图层顺序；
- 调整网格密度；
- 修复蒙版；
- 修改参数范围；
- 调整物理强度；
- 显示破图和穿模风险；
- 导出开放模型格式。

### Milestone 4：通用性测试

使用不少于 5 个不同来源、不同发型和不同服装的合规 Q 版角色测试。

重点测试：

- 短发与长发；
- 裙装与裤装；
- 裸足与鞋子；
- 简单饰品；
- 不同头身比例；
- 不同眼睛和嘴巴画法。

## 11. MVP 验收标准

v0.1 被视为可用，需要至少满足：

- 能导入规范化 PSD 或 PNG 图层目录；
- 输入错误会给出明确提示；
- 能正确还原图层顺序和角色外观；
- 能生成并播放眨眼动作；
- 能生成嘴巴开合动作；
- 能生成眼球跟随；
- 能生成呼吸和待机摆动；
- 至少一种头发物理效果可用；
- 参数可以在界面中手动调节；
- 项目保存后可以无损重新加载；
- 至少在 3 个不同 Q 版角色上完成完整流程；
- 核心流程有自动化测试；
- 不依赖 Live2D Cubism Core 才能运行。

## 12. 主要技术难点

### 12.1 图层拆分

单张图片中大量区域互相遮挡。系统不仅需要分割可见部分，还需要补全隐藏区域。

应对方式：

- 第一阶段使用人工分层输入；
- 第二阶段复用现有拆层模型；
- 提供蒙版修正工具；
- 对输入姿态和画风设置明确限制。

### 12.2 自动网格

过于稀疏的网格会导致动作僵硬，过于密集则会增加计算和编辑成本。

应对方式：

- 按图层语义使用不同网格策略；
- 眼皮、嘴巴和头发使用专用模板；
- 大块身体区域采用较稀疏网格；
- 边缘和弯曲区域提高网格密度。

### 12.3 通用绑定

不同角色的脸型、发型和服装差异较大，单一模板无法覆盖所有情况。

应对方式：

- 首先只支持 Q 版正面角色；
- 建立多种部件模板；
- 根据关键点和轮廓缩放模板；
- 保留人工调整入口；
- 用多角色测试而不是只测试亚托莉。

### 12.4 质量检测

自动生成的模型可能出现裂缝、穿模、边缘空洞或不自然形变。

应对方式：

- 检查相邻图层是否存在空洞；
- 检查关键参数极值下的透明区域；
- 保存参数快照并生成质量报告；
- 在编辑器中标记高风险位置。

## 13. 可参考的开源项目

> 以下项目适合作为技术参考或候选依赖。正式引入前，需要再次核查仓库的最新状态、代码许可证、模型权重许可证和第三方依赖。

### 13.1 See-through

- 仓库：`https://github.com/shitagaki-lab/see-through`
- 用途：单张二次元角色立绘的语义拆层、遮挡补全和图层顺序推断。
- 项目能力：将单张二次元立绘转换为带透明通道的语义图层，并导出分层结果。
- 对本项目的价值：可作为 v0.2 单图拆层模块的重要参考或候选基础。
- 注意事项：
  - 属于研究型项目；
  - 推理环境和模型体积可能较重；
  - 输出结果仍可能需要人工修正；
  - 需要单独核查模型权重和训练数据条款。

### 13.2 image2live2d

- 仓库：`https://github.com/Wzhang3912/image2live2d`
- 用途：从分层角色图生成可绑定 2D 人偶，并尝试输出 nijilive 和 Cubism 相关格式。
- 已展示的方向：
  - 网格生成；
  - 自动绑定；
  - 眨眼；
  - 口型；
  - 视线；
  - 头部动作；
  - 头发和衣服物理。
- 对本项目的价值：
  - 是与本项目目标较接近的端到端参考；
  - 可以重点研究其中间表示、自动绑定规则、测试方式和导出流程。
- 注意事项：
  - 项目处于较早阶段；
  - 不应直接视为稳定的生产依赖；
  - 更适合用于验证技术路线和比较实现方案。

### 13.3 Inochi2D SDK

- 仓库：`https://github.com/Inochi2D/inochi2d`
- 用途：实时 2D 人偶动画运行库和开放人偶格式的参考实现。
- 对本项目的价值：
  - 参考图层、网格、参数、变形和渲染的数据结构；
  - 作为首版开放输出格式和运行时候选；
  - 避免项目核心依赖专有 Cubism Core。

### 13.4 Inochi Creator

- 仓库：`https://github.com/Inochi2D/inochi-creator`
- 用途：Inochi2D 模型绑定编辑器。
- 对本项目的价值：
  - 参考网格编辑、参数面板、变形器树和物理配置界面；
  - 研究一个完整 2D 人偶编辑器的交互设计；
  - 对比自动绑定结果与人工绑定流程。

### 13.5 nijilive

- 仓库：`https://github.com/nijigenerate/nijilive`
- 用途：实时 2D 人偶动画库和 nijilive Puppet 标准参考实现。
- 对本项目的价值：
  - 可作为开放运行时和输出格式候选；
  - 可参考网格实时变形、参数查询和多图形后端设计。

### 13.6 nijigenerate

- 仓库：`https://github.com/nijigenerate/nijigenerate`
- 用途：nijilive 格式的开源绑定编辑器。
- 对本项目的价值：
  - 可用于检查和继续编辑自动生成结果；
  - 可参考编辑器中的参数、网格、绘制顺序和标准绑定设计；
  - 可评估将其格式作为首版导出目标的可行性。
- 注意事项：
  - 项目成熟度需要单独评估；
  - 集成前应进行格式和兼容性测试。

### 13.7 psd-tools

- 仓库：`https://github.com/psd-tools/psd-tools`
- 用途：在 Python 中读取、解析和有限编辑 PSD/PSB 文件。
- 对本项目的价值：
  - 导入分层 PSD；
  - 获取图层名称、层级、位置和像素内容；
  - 导出图层图像；
  - 构建输入规范检查器。
- 注意事项：
  - PSD 规范复杂；
  - 部分 Photoshop 高级特性可能无法完整支持。

### 13.8 rembg

- 仓库：`https://github.com/danielgatis/rembg`
- 用途：自动移除图片背景。
- 对本项目的价值：
  - 作为 v0.2 的输入预处理模块；
  - 处理没有透明背景的立绘。
- 注意事项：
  - 通用抠图模型对发丝和二次元细节不一定稳定；
  - 后期可能需要二次元专用模型或人工修正工具。

### 13.9 MediaPipe

- 仓库：`https://github.com/google-ai-edge/mediapipe`
- 用途：摄像头人脸关键点、姿态识别和实时媒体处理。
- 对本项目的价值：
  - 驱动模型的眨眼、嘴巴、视线和头部倾斜；
  - 构建实时预览和摄像头驱动测试；
  - 不负责立绘本身的拆层和绑定。

## 14. 开源与许可证策略

### 14.1 项目代码许可证

建议主项目使用：

- Apache-2.0；或
- MIT。

暂时更推荐 Apache-2.0，因为项目可能包含较多算法实现，并可能组合多个 Apache-2.0、MIT 和 BSD-2-Clause 依赖。

最终选择前应检查：

- 是否需要明确的专利授权条款；
- 计划接受的第三方贡献方式；
- AI 模型权重是否允许再分发；
- 示例角色素材是否具有再分发授权。

### 14.2 模型与代码分离


### 14.3 Live2D / Cubism 边界

项目核心不应依赖 Cubism Core。

原因：

- Cubism Core 是专有组件；
- 使用 Cubism SDK 发布软件时可能存在独立许可要求；
- 将其作为核心依赖会限制项目的完全开源属性和发行方式；
- Cubism 相关格式可能存在兼容性和授权边界。

因此：

- 核心模型格式使用项目自定义开放格式；
- 首选 Inochi2D 或 nijilive 作为开放导出方向；
- Cubism 兼容功能放在可选导出插件中；
- 在正式发布 Cubism 相关功能前，单独核实官方许可；
- 项目名称和宣传避免将“Live2D”当作通用格式名称。

## 17. 当前结论

本项目具有明确的技术可行性。

现有开源生态已经覆盖：

- 单张二次元立绘拆层；
- 背景移除；
- PSD 解析；
- 2D 网格变形；
- 开放人偶格式；
- 绑定编辑器；
- 人脸跟踪和实时驱动；
- 早期端到端自动绑定原型。

项目的主要工作不在于从零发明所有技术，而在于：

1. 为正面 Q 版角色定义严格、可验证的输入规范；
2. 设计稳定的中间数据格式；
3. 将拆层、网格、绑定、物理和预览模块连接成完整流程；
4. 为不同角色建立可复用的绑定模板；
5. 提供简单有效的人工修正工具；
6. 通过多个角色持续验证通用性和生成质量。

第一版应从“分层输入自动绑定”开始，而不是直接挑战完整单图一键生成。
